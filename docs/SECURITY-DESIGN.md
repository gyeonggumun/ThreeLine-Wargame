# 팀장 역할 · 의도한 취약점과 운영 권한의 경계

## 목표와 본인 역할

팀장으로서 SSH 접속 제한, 방화벽, sudo·파일 권한, 서비스 계정 분리, 문제 간 접근 차단을 맡았습니다. 목표는 문제에 의도한 취약점은 유지하고, 이를 넘어서는 접근과 다른 문제로의 확산을 줄이는 것이었습니다.

아래의 상태는 제출용 OVA를 읽기 전용으로 분석한 결과입니다. 설정 파일·계정·소유권·모드의 존재를 확인한 것이며, 실행 중 정책의 전체 적용 여부나 완전한 격리를 증명하는 결과는 아닙니다.

## 통제별 확인 결과

| 영역 | 제출본에서 확인한 내용 | 문서에서 주장할 수 있는 범위 |
| --- | --- | --- |
| 방화벽 | `ENABLED=yes`, 수신·전달 기본 DROP, 출력 기본 ACCEPT | 불필요한 수신 진입점을 줄이도록 구성 |
| IPv4·IPv6 | 모두 HTTP 80과 SSH 22 허용 | IPv6 규칙도 존재; SSH 출발지 제한은 없음 |
| 내부 포트 | 담당 Flask 앱이 `127.0.0.1:8080` 수신 | 외부 직접 접속 경로 축소 |
| 서비스 계정 | `wargame`, `hiddenarchive`, `www-data`, `mysql` 분리 | 서비스 권한을 root와 분리 |
| 로그인 셸 | Flask 계정·www-data는 `nologin`, mysql은 `/bin/false` | 해당 서비스 계정의 대화형 로그인 제한 |
| sudo | 표준 root/admin/sudo 규칙, sudoers.d에 별도 서비스 계정 규칙 없음 | 확인한 범위에 서비스 계정의 직접 sudo 허용·sudo 그룹 소속 없음 |
| 권한 상승 제한 | 두 Flask 서비스에 `NoNewPrivileges=true` | 새 exec를 통한 권한 획득을 제한하는 설정 존재 |
| 임시 공간 | 두 Flask 서비스에 `PrivateTmp=true` | 서비스별 임시 디렉터리 분리를 구성 |
| 소스 파일 | 담당 앱 디렉터리 0700, app.py 0600 | 다른 일반 계정의 직접 읽기·탐색 축소 |
| 별도 앱 경계 | Hidden Archive 디렉터리 0750, 소스·목표 파일 0640 | 소유 계정과 그룹 중심으로 접근 범위 제한 |

원본 설정: [담당 앱 서비스](../reference/systemd/wargame.service), [별도 앱 서비스](../reference/systemd/hidden-archive.service), [UFW 기본값](../reference/ufw/defaults.conf), [IPv4 규칙](../reference/ufw/user.rules), [IPv6 규칙](../reference/ufw/user6.rules).

## 파일 권한과 계정 경계

| 경로 | 소유자:그룹 | 모드 | 해석 |
| --- | --- | --- | --- |
| `/var/www/wargame` | wargame:wargame | 0700 | 해당 계정 중심의 디렉터리 접근 |
| `/var/www/wargame/app.py` | wargame:wargame | 0600 | 일반 다른 계정의 소스 읽기 제한 |
| `/var/www/hidden-archive` | hiddenarchive:hiddenarchive | 0750 | 소유자·그룹 탐색 허용 |
| Hidden Archive의 `secret/flag2.txt` | hiddenarchive:hiddenarchive | 0640 | 다른 계정의 일반 읽기 제한 |
| `/etc/ch2_flag.txt` | root:wargame | 0777 | 모든 로컬 계정의 읽기·쓰기 허용; 재정비 대상 |
| `/etc/wargame-progress/secret.key` | root:wargame-progress | 0640 | 진행도 공유 그룹 읽기 허용 |

권한 모드는 ext4 inode에서 직접 확인했습니다. 숫자 UID·GID와 일부 서비스 계정 정보는 [evidence.json](evidence.json)에 기록했습니다. 플래그와 키의 내용은 공개하지 않습니다.

## SSH: 담당한 통제와 제출 상태의 차이

서비스 계정의 로그인 셸 제한은 확인할 수 있습니다. 그러나 제출본의 UFW는 22번 포트를 모든 출발지에 허용하며, `/etc/ssh/sshd_config.d/50-cloud-init.conf`에는 `PasswordAuthentication yes`가 있습니다. 메인 파일의 활성 지시문에서는 `AllowUsers`, `AllowGroups`, 관리망 출발지 제한을 확인하지 못했습니다.

따라서 이 제출본을 **관리자 IP만 SSH 허용**, **비밀번호 인증 비활성화**, **SSH 완전 차단**으로 소개하지 않습니다. 이런 요구를 최종 정책으로 삼으려면 관리망 허용 목록, 인증 방식, 실제 `sshd` 설정 및 접속 시험을 별도로 확인해야 합니다. root 로그인도 주석에 있는 값을 실제 적용값으로 간주하지 않았습니다.

## 문제 간 격리의 실제 범위

1. **Challenge 1·2는 같은 계정과 프로세스입니다.** 2번에서 얻은 명령 실행은 이 계정이 읽을 수 있는 앱 소스·DB 연결 설정 등에도 영향을 줄 수 있습니다.
2. **모든 PHP 문제를 서로 다른 OS 계정으로 나누었다는 근거는 없습니다.** 공통 웹 실행 권한 아래의 읽기·쓰기 가능 범위를 따로 점검해야 합니다.
3. **`NoNewPrivileges`는 파일 접근 차단 기능이 아닙니다.** 이미 가진 UID·그룹 권한을 통한 읽기·쓰기와 네트워크 요청은 별도의 통제가 필요합니다.
4. **`PrivateTmp`는 전체 파일시스템 격리가 아닙니다.** `/etc`나 다른 서비스 경로를 자동으로 숨기지 않습니다.
5. **진행도 서명 키는 공유 그룹이 읽습니다.** `www-data`, `wargame`, `hiddenarchive`가 `wargame-progress` 그룹에 포함됩니다. 그룹 내 서비스 침해가 서명 신뢰로 확산될 가능성을 검토해야 합니다.
6. **문제 파일의 과도한 권한이 남아 있습니다.** `0777` 플래그는 다른 계정의 접근뿐 아니라 파일 변조와 실습 훼손 가능성도 만듭니다.

이는 통제를 적용하지 않았다는 의미가 아니라, **적용한 통제가 다루는 경계와 다루지 못하는 경계를 구분한 분석**입니다.

## 후속 개선 및 검증 기준

아래는 제출본에 적용 완료된 기능이 아니라 후속 개선안입니다.

| 과제 | 개선 방향 | 검증 기준 |
| --- | --- | --- |
| SSH 관리 경로 | 관리망 허용 목록과 인증 정책 확정 | 허용·비허용 출발지 및 계정의 접속 결과 비교 |
| 목표 파일 권한 | 불필요한 쓰기·실행 비트 제거 | 담당 계정 읽기 성공, 다른 계정 읽기·쓰기 실패 |
| 담당 문제 분리 | 문제별 계정·DB 자격 증명 또는 컨테이너 경계 검토 | 2번 명령 실행으로 1번 소스·DB 자격 증명 접근 불가 |
| 공통 PHP 권한 | 문제별 실행 주체와 쓰기 경로 분리 | 타 문제 파일·완료 정보 변조 불가 |
| 진행도 서명 | 문제별 키·목표 범위 또는 검증 전용 서비스 분리 | 한 서비스의 권한으로 다른 문제 완료를 기록할 수 없음 |
| 출력 통신 | 실습 요구에 맞는 목적지 범위 정의 | 허용한 리스너 접근은 성공, 관리 서비스 접근은 실패 |
| 운영 계정·소스 | root 소유 읽기 전용 배포와 필요한 쓰기 경로 분리 | 앱 계정이 실행 소스와 서비스 설정을 바꿀 수 없음 |
| 반복 재현 | 초기화 가능한 VM과 통제 회귀 검증 | 문제 풀이 성공과 경계 위반 실패를 함께 확인 |

핵심 학습은 취약한 기능을 의도적으로 배치하는 것과 운영 권한을 무제한으로 허용하는 것을 구분하는 일입니다. 포트폴리오에서는 보안 설정을 맡았다는 역할, 실제 적용 근거, 남은 제약을 함께 설명합니다.
